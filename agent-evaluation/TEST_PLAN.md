# SnapNote Agent 离线评测与知识定位实验方案

## 1. 目标与拟验证结论

本方案用于产生可复现、可审计的产品评测证据，验证 SnapNote 能否从课程录屏、产品演示和访谈视频中提取关键页面、控制重复画面，并帮助用户更快定位知识点。

目标结论示例：

> 基于 30 条、累计 18 小时的课程录屏、产品演示及访谈视频构建离线评测集，关键页面覆盖率达到 93.2%，重复画面率控制在 6.8%；在 60 个知识点查找任务中，用户中位定位时间由 3 分 18 秒缩短至 27 秒，定位效率提升 86%。

以上数字是**验收目标，不是预设结果**。只有实测值满足相应条件时才能使用；若未达到，应报告真实结果和失败分层，不得选择性剔除样本。

## 2. 评测范围

受测链路：

```text
视频输入 → 视频解析 → ASR → 镜头检测 → 关键帧选择与去重
        → OCR/视觉理解 → 图文时间对齐 → 结构化笔记与时间锚点
```

本轮覆盖：

- MP4、MOV、WebM 视频的完整离线处理。
- 课程录屏、产品演示、访谈三类内容。
- 关键页面召回、输出重复、时间锚点和知识点可定位性。
- 端到端成功率、处理耗时及失败案例。
- 原始视频基线与 SnapNote 结果页的用户对照实验。

本轮不把摘要文风偏好、商业转化率和长期学习效果作为主指标；可记录为探索性指标，但不能混入主结论。

## 3. 核心指标与验收门槛

| 指标 | 唯一定义 | 目标/门槛 | 聚合方式 |
| --- | --- | --- | --- |
| 关键页面覆盖率 | 被至少一个有效输出关键帧命中的 Gold 关键页面数 / Gold 关键页面总数 | ≥ 93.2% | 30 条视频合并后的 micro 值为主，同时报告逐视频 macro 值 |
| 重复画面率 | 输出帧中除每个等价页面簇首张外的多余帧数 / 全部有效输出帧数 | ≤ 6.8% | 30 条视频合并后的 micro 值为主 |
| 时间锚点命中率 | 点击锚点后落入 Gold 证据区间或距区间边界不超过 15 秒的任务数 / 全部任务数 | ≥ 90% | 60 个知识点任务合并统计 |
| SnapNote 中位定位时间 | 从展示问题到用户提交正确时间点的耗时中位数 | ≤ 27 秒 | 60 次 SnapNote 条件试次；失败按 480 秒计入主分析 |
| 相对定位效率提升 | `(基线中位时间 - SnapNote 中位时间) / 基线中位时间 × 100%` | ≥ 86% | 使用未四舍五入的秒数计算，最后再展示 |
| 知识定位成功率 | 在 8 分钟内提交正确证据时间点的试次数 / 全部试次数 | SnapNote 不低于基线，且建议 ≥ 90% | 分条件报告 |
| 端到端任务成功率 | 无人工干预生成完整结果的成功视频数 / 30 | ≥ 90% | 逐视频统计 |

补充指标：逐类型覆盖率与重复率、时间锚点绝对误差 P50/P90、ASR 字错率抽样、图文对齐正确率、实时系数（处理秒数/视频秒数）、模型调用量和单小时视频成本。

### 3.1 关键口径说明

- “关键页面”不限于 PPT 页，也包括产品界面状态、图表、代码、白板结论或访谈中承载关键信息的画面；纯装饰转场、黑屏和重复动画中间态不计。
- 同一页面的小幅鼠标移动、讲师头像变化、字幕变化或压缩噪声归入同一等价页面簇；若动画新增内容改变了知识含义，则标为新页面。
- “重复画面率”衡量最终交付物中仍残留的冗余，不等同于“重复过滤率”。两者不得混用。
- 3 分 18 秒等于 198 秒；从 198 秒降至 27 秒的降幅为 `86.36%`，可按整数展示为 `86%`。若实测中位数不是这两个值，必须用实测值重新计算。

## 4. 正式离线评测集

### 4.1 规模与配额

正式集固定为 30 条视频，总时长以 `ffprobe` 读取值累计为 18 小时（允许因封装时长产生不超过 60 秒的总误差）。建议配额：

| 类型 | 条数 | 目标累计时长 | 典型内容 |
| --- | ---: | ---: | --- |
| 课程录屏 | 12 | 约 8 小时 | PPT、代码演示、图表、讲师画中画、中英混合 |
| 产品演示 | 10 | 约 4 小时 | Web/桌面/移动端操作、弹窗、菜单、状态变化 |
| 访谈视频 | 8 | 约 6 小时 | 单人/双人/多人、字幕、插图、少量 B-roll |
| 合计 | 30 | 18 小时 | — |

数据集还应覆盖：720p/1080p/更高分辨率，不同帧率与码率，中文/英文/中英混合，静态与高动态画面，清晰与轻度模糊素材，以及 15–90 分钟的时长区间。

### 4.2 防止数据泄漏

- 30 条正式视频及其标注在评测前冻结并生成 SHA-256。
- 阈值、Prompt、模型和后处理规则只能使用额外的试验视频调整；正式集不得反复查看后调参。
- 每次正式运行写入唯一 `run_id`，保存 Git commit、模型版本、Provider、Prompt 哈希、环境变量白名单、ffmpeg/ffprobe 版本、硬件和运行时间。
- 模型或算法发生实质变化后必须生成新运行，不得将不同版本的最佳单项指标拼接成一组结果。

### 4.3 数据清单字段

`dataset/manifest.csv` 至少包含：

```text
video_id,category,local_path,sha256,duration_s,width,height,fps,codec,
language,layout,difficulty,source,license_status,privacy_status,dataset_version
```

`local_path` 可指向本机不入库的视频；禁止把个人信息、密钥或未经授权的媒体提交到仓库。

## 5. Gold 标注规范

### 5.1 关键页面与重复簇

`annotations/gold_pages.csv` 每行一个 Gold 页面：

```text
video_id,page_id,cluster_id,start_s,end_s,page_type,is_key,
importance,description,ocr_hint,annotator,review_status
```

标注步骤：

1. 标出页面首次稳定可读时间与最后有效时间。
2. 为语义相同的页面分配同一 `cluster_id`。
3. 标记页面类型、是否关键、重要度和可用于核验的文字/视觉提示。
4. 动画仅在新增内容改变可回答的知识时拆分页面。
5. 对无法判断、严重遮挡或本身不可读的区间标记为不可评测，不进入分母。

### 5.2 知识点与证据区间

每条视频设计 2 个可客观核验的知识点任务，共 60 个。`annotations/knowledge_tasks.csv` 至少包含：

```text
task_id,video_id,question,answer,primary_start_s,primary_end_s,
alternate_intervals,difficulty,task_type,required_visual_evidence,
required_audio_evidence,annotator,review_status
```

任务类型建议均衡覆盖：事实定义、步骤定位、参数/数字、因果解释、视觉界面状态、跨语音与画面联合判断。问题不能直接泄露时间点或页面标题。

### 5.3 标注质控

- 100% 样本由一名标注者初标，至少 20% 由第二名标注者盲复标。
- 页面是否等价、知识答案是否正确和证据区间冲突均由第三人仲裁。
- 报告复标一致率；页面等价判断建议 Cohen's kappa ≥ 0.80，证据区间边界差异的中位数建议 ≤ 5 秒。
- 标注者不能看到受测系统的最终输出，以减少迎合模型结果的偏差。

## 6. 离线运行与计分

### 6.1 运行前锁定

在 `configs/<run_id>.yaml` 记录：

- 数据集与标注版本。
- Git commit 和工作区是否干净。
- ASR、视觉模型、LLM、Prompt 版本及采样参数。
- 场景检测、清晰度、pHash、OCR 和动态代理阈值。
- 操作系统、CPU/GPU、内存、ffmpeg 版本和网络条件。
- 重试、超时、并发和缓存策略。

正式运行前执行已有工程测试：

```powershell
cd frontend
npm.cmd run lint
npm.cmd test

cd ../backend
conda run -n snapnote python -m compileall -q app
conda run -n snapnote python -m unittest discover -s tests -v
```

### 6.2 批量运行

1. 清空本轮专用输出目录，不删除历史运行。
2. 按 `manifest.csv` 顺序处理 30 条视频，并记录每一阶段的开始、结束、错误和重试。
3. 保存逐视频输出帧、时间戳、OCR、转写、笔记块、最终 Markdown 和 `pipeline_stats`。
4. 固定配置至少完成一次完整正式运行；如模型存在随机性，建议运行 3 次并同时报告均值、标准差和最差一次，主结论采用预先约定的一次或三次均值。
5. 失败样本不得静默重跑后只保留成功结果。所有尝试都要记录，端到端成功率以预注册的重试策略计算。

### 6.3 页面匹配

输出帧与 Gold 页面采用一对一匹配：

1. 根据时间交集、pHash/SSIM 和 OCR 文本相似度生成候选匹配。
2. 由不知道系统版本的评审者确认候选是否语义等价。
3. 一个输出帧最多命中一个 Gold 页面；一个 Gold 页面被多帧命中时只计一次覆盖，其余计为重复候选。
4. 输出黑屏、转场、不可读或无信息画面记为无效帧，另报无效画面率。

计算公式：

```text
关键页面覆盖率 = 已命中的 Gold 关键页面数 / Gold 关键页面总数
重复画面率     = 等价簇内多余输出帧数 / 全部有效输出帧数
```

必须同时输出：总体 micro 值、30 条视频的 macro 均值、三类内容分层值、逐视频明细、95% bootstrap 置信区间和最差 5 个案例。

### 6.4 锚点与知识点自动评测

- 对每个知识任务，让系统返回最相关笔记块及其时间锚点，保留 top-1 和 top-3。
- top-1 锚点落入任一 Gold 证据区间，或距最近边界不超过 15 秒，判为命中。
- 同时报告 top-1/top-3 命中率、绝对时间误差 P50/P90、无答案率和错误答案率。
- 自动 Agent 或浏览器脚本可用于回归和预筛，但它的耗时只能叫“Agent 定位耗时”，不能替代“用户定位时间”。

## 7. 60 个知识点用户定位实验

### 7.1 实验设计

采用随机、对照、交叉设计：

- 条件 A（基线）：原始视频播放器，仅有播放、暂停和进度条；若产品主张针对“视频 + 原始转写”，则必须明确改用该基线并在报告中写明。
- 条件 B（SnapNote）：视频播放器 + 自动生成的图文笔记、知识点和时间锚点。
- 60 个唯一问题在两个条件下各完成一次，共 120 次有效试次。
- 至少 12 名未看过测试视频的目标用户，每人完成 10 次试验：5 次基线、5 次 SnapNote。
- 同一参与者不能在两个条件下看到同一问题或同一知识点，避免记忆污染。
- 使用拉丁方或等价的分层随机方法平衡条件顺序、内容类型、题目难度和参与者熟练度。

若要把结论用于正式市场宣传，建议在实验前完成样本量/功效分析并预注册；12 人、60 对任务适合作为产品验证的最低规模，不应被描述为大规模用户研究。

### 7.2 单次任务流程

1. 展示问题时启动计时，用户此前不能预览对应视频或笔记。
2. 用户在指定条件中查找答案，并点击/填写能够证明答案的视频时间点。
3. 用户提交答案与时间点时停止计时。
4. 答案正确且提交点落入 Gold 区间或距边界不超过 15 秒，记为成功。
5. 8 分钟仍未成功则终止，记为失败；主分析将其耗时按 480 秒计入，另做生存分析或成功样本敏感性分析。
6. 每次记录条件、参与者、题目、开始/结束时间、答案、提交时间点、是否正确、点击次数和异常事件。

不得人工暂停计时、提示页面位置或剔除“找得太慢”的正常用户。技术故障可剔除，但必须记录原因并按预注册规则补测。

### 7.3 统计方法

- 主结果：两个条件各 60 次试次的中位定位时间和成功率。
- 配对分析：按 60 个任务配对条件 A/B 的耗时，使用 Wilcoxon 符号秩检验；同时报告中位差和效应量。
- 置信区间：以任务为主、参与者为簇进行 bootstrap，报告中位数与效率提升的 95% CI。
- 分层结果：课程/产品/访谈、简单/中等/困难、纯语音/纯视觉/多模态。
- 顺序效应：比较先做 A 与先做 B 的参与者；若差异明显，在报告中说明。

定位效率提升按未取整数据计算：

```text
improvement_pct = (median_baseline_s - median_snapnote_s)
                  / median_baseline_s * 100
```

## 8. 发布门禁与结论规则

### 8.1 通过条件

只有同时满足以下条件，才可发布完整目标结论：

1. 正式数据集确为 30 条，总时长经工具校验为约 18 小时，三类内容配额满足约定。
2. 关键页面覆盖率实测 ≥ 93.2%，并附 Gold 页面总数和 95% CI。
3. 重复画面率实测 ≤ 6.8%，并附有效输出帧总数和 95% CI。
4. 用户实验具备 60 个唯一任务、两个条件各 60 次有效试次，且 SnapNote 中位时间 ≤ 27 秒、相对提升 ≥ 86%。
5. SnapNote 的定位成功率不低于基线；不存在用速度换取明显正确率下降的情况。
6. 无数据泄漏、隐私/授权问题、选择性剔除或版本拼接。

若只满足部分条件，就只发布已被支持的子结论。例如覆盖率达标但用户实验未完成时，不得提前声称定位效率提升。

### 8.2 数字展示规则

- 百分比内部保留至少 4 位小数，报告展示 1 位；效率提升可按文案需要展示整数，但必须由原始秒数计算。
- “达到”用于越高越好的指标，“控制在/不高于”用于越低越好的指标。
- 报告必须明确基线能力，不能只写“传统方式”。
- 小数位不能制造虚假精度；同时给出分子/分母，例如 `233/250 = 93.2%`。
- 对外文案要注明测试集构成、运行日期、系统版本和实验样本量。

## 10. 建议执行顺序

1. 建立 30 条视频清单并校验授权、SHA-256 和总时长。
2. 完成关键页面、重复簇、知识点及证据区间标注与复标。
3. 用正式集之外的视频调参，随后锁定配置和代码版本。
4. 运行工程测试和 30 条视频端到端离线评测。
5. 盲审页面匹配，生成覆盖率、重复率、锚点和失败分层。
6. 冻结 SnapNote 结果页，实施 60 题、双条件用户定位实验。
7. 运行统计脚本，生成机器可读结果、报告和失败案例。
8. 由非实现者复核分母、剔除记录、公式和对外文案后发布。

## 11. 停止条件与回归策略

- 数据泄漏、Gold 标注与系统输出相互污染、正式集在运行中被替换时，本轮作废。
- 超过 10% 视频端到端失败时，先修复稳定性，再进行用户实验。
- 覆盖率或重复率未过门槛时，保留本轮结果作为基线；用非正式数据调优后创建新 `run_id` 全量重跑。
- 后续每次改动至少回归全部 30 条视频；若成本受限，可另建小型 smoke 集用于日常检查，但发布前仍需跑冻结正式集。
